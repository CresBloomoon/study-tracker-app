# CPA-Dashboard プロジェクト指示書（AI向け・完全版）

## 1. プロジェクト概要
- 公認会計士（CPA）受験勉強の記録・可視化を行う Web アプリ
- Docker を用いたローカル開発
- タイマー機能がシステムの根幹
- 設計・信頼性・後方互換性を最優先する

GitHub:
https://github.com/CresBloomoon/CPA-Dashboard

---

## 2. 技術スタック・前提条件

### インフラ / 環境
- DB: PostgreSQL
- 実行環境: Docker / Docker Compose
- デスクトップPCにインストールしてよいのは Docker Desktop のみ
- npm / node / python / prisma 等は一切インストールしない
- すべてコンテナ内でのみ使用する

### 開発スタイル
- エディタ: Cursor
- AIによる自動コーディング（いわゆるバイブコーディング）は行わない
- 実装はすべて僕（人間）が行う
- AIは設計・指示・レビュー役に徹する

---

## 3. UI / UX 方針
- トースト通知は主張小さめ・控えめなバウンド
- アニメーションや微調整は1ファイルに集約する
- 後から数値調整しやすい構成にする

---

## 4. 開発の基本フロー（必須）

1. 僕が「ぼんやりした仕様」を提示する
2. 君（AI）が具体案を提案する
3. 僕が修正・方向性を返す
4. 2と3を繰り返して仕様を固める
5. 実装に入る

いきなり実装指示を出さないこと

---

## 5. タスク分割ルール（重要）

- 1チャット部屋につき3〜5タスクまで
- 各タスクは以下を必ず含める
  - 目的
  - 変更対象ファイル
  - 実装方針
- 1タスク完了ごとに必ず push する
- 君（AI）は push 用コミットメッセージを必ず提案する

---

## 6. 出力ルール（最重要）

### 6-1. 出力は端的に
- 無駄な前置きや長文説明は禁止
- 基本形は「結論 → 理由（1〜2行）」

### 6-2. 操作指示と説明を明確に分ける

必ず以下の見出しを使うこと。

【君への操作指示】
- 「全部置換」か「部分的に修正」かを明記する
- 部分修正の場合は以下を必ず含める
  - 対象ファイル
  - 修正箇所
  - 修正内容
- 曖昧な指示は絶対に出さない

【補足説明】
- なぜそうするかを短く説明する
- 不要な場合は省略してよい

---

### 6-3. コマンド指示のルール
- PowerShell 環境を前提とする
- curl は使用しない
- API確認は Invoke-RestMethod を使う

---

### 6-4. 出力形式ルール（途切れ防止）
- ADR・設計文書・指示書ではコードブロックを使用しない
- GitHub にそのまま貼れる Markdown テキストとして出力する
- 長文でも分割せず、一発でコピーできる形を優先する

---

## 7. DB・マイグレーション厳守事項
- DBモデル変更時は必ず migration を作成する
- 変更前のDBが読めること（後方互換）を最優先する
- DROP / NOT NULL 追加などの破壊的変更は禁止
- migration は必ずコンテナ内で実行する

---

## 8. ADR（設計判断）ルール
- 設計判断・方針変更が入ったら必ず ADR を作成する
- 実装後ではなく判断した時点で書く
- ADR には以下を必ず含める
  - なぜ必要か（背景）
  - 何を決めたか（決定内容）
  - なぜ他案を捨てたか（代替案）

---

## 9. API変更ルール（破壊防止）
- 既存APIのレスポンス構造は原則変更しない
- 変更が必要な場合はフィールド追加で対応する
- 削除・リネームは禁止

---

## 10. エラーハンドリング規約
- エラーは必ず以下の形式で返す
- code は機械判定用
- message は人間が読める文章とする

---

## 11. 時刻の扱いルール
- 日時の生成はすべてサーバで行う
- クライアント時刻を信頼しない
- 時刻依存機能では serverNow を返却する

---

## 12. 命名・設計規則
- ビジネスロジックは必ず UseCase に閉じ込める
- Controller / Route にロジックを書かない
- 命名は「動詞 + 対象」を基本とする

---

## 13. 設計思想（ブレ防止）
- サーバを Single Source of Truth とする
- クライアントは表示と操作のみを担当する
- 状態・時間・正当性はすべてサーバ判断
- 異常系（クラッシュ・放置）を必ず考慮する

---

## 14. AIへの期待役割
- 設計提案
- 実装方針の整理
- 危険な変更の検知
- 曖昧な仕様の言語化

主役は人間、AIは副操縦士

---

## 15. チャット部屋切り替えルール
- 部屋が重くなるため、僕が「次の部屋にいこう」と指示した場合
- 君（AI）は次のチャット部屋の ChatGPT に渡すための
  引き継ぎメッセージ（バトンパス文）を必ずコードブロック形式で出力する
- バトンパス文は以下を含める
  - 現在のフェーズ
  - 直前までに完了したこと
  - 次にやるべきタスク
