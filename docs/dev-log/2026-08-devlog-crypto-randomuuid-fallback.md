# crypto.randomUUID() 未対応環境向けフォールバック実装

> これは設計判断の記録（ADR）ではなく、作業内容の記録（開発ログ）である。

- 対象: バグ修正（Step番号には対応しない単発対応）
- 日付: 2026-08-02

## 概要

`http://homepi:5175` のような非セキュアコンテキスト（HTTPの独自ホスト名）でタイマー画面にアクセスすると、`crypto.randomUUID is not a function` エラーによりタイマーの開始・一時停止・再開・記録の全操作が失敗する不具合を修正した。

原因は、`crypto.randomUUID()` がブラウザのセキュアコンテキスト（HTTPS、またはホスト名が文字通り`localhost`／ループバックIP）でのみ利用可能なAPIであること。本アプリのスタックにはTLS終端の仕組みが存在せず（`docker-compose.yml`は平文HTTPで`5175:3000`をマッピングしているのみ）、`homepi`という独自ホスト名でのアクセスはW3C Secure Contexts仕様上「潜在的に信頼できるオリジン」の定義に該当しないため、`window.crypto`オブジェクト自体は存在するが`randomUUID`メソッドのみが未定義になっていた。

対応方針は、`uuid`等の外部ライブラリを追加せず、`crypto.randomUUID()`が使える場合はそれを使い、使えない場合は非セキュアコンテキストでも利用可能な`crypto.getRandomValues()`でRFC4122準拠のUUID v4を自前で組み立てるフォールバック関数を実装する形とした（まーくんの判断、B案）。`clientRequestId`は重複送信防止用の識別子であり、厳密な暗号学的ランダム性までは要求しない用途のため、この実装で十分と判断している。

## 変更ファイル一覧と責務

- `frontend/lib/ui/uuid.ts`（新規）
  UUID v4生成の共通ヘルパー`generateUuid()`。`crypto.randomUUID`が使える場合はそれを使い、未対応の場合は`crypto.getRandomValues()`によるフォールバックを行う。将来的に他の箇所でもID生成が必要になった場合の再利用を想定し、用途名（clientRequestId）ではなく技術名（uuid）でファイルを切った。
- `frontend/features/timer/hooks/useStudyTimer.ts`
  タイマー開始・一時停止・再開・記録（ストップウォッチ/ポモドーロ）・手動記録の5箇所の`clientRequestId`生成を、直接の`crypto.randomUUID()`呼び出しから`generateUuid()`呼び出しに置き換えた。

## ADRの要否判断

**不要と判断（dev-logのみで対応）**。理由：本対応はブラウザAPIの可用性という実行環境の制約に対する技術的フォールバックであり、ADR-018のようなドメインルール・データモデル・API契約に関わる設計判断ではないため。まーくんにも同判断で確認済み。

## ビルド確認結果

- サンドボックス環境からの確認：
  - フォールバックロジック単体をNode.jsで検証し、`randomUUID`が使える場合・使えない場合（フォールバック）のいずれも正しいUUID v4形式（`v4Regex`一致）で、100回生成して重複がないことを確認済み。
  - `next dev`（ホットリロード）に対して`/timer`ページをリクエストし、ビルドエラーなく200が返ることを確認済み（構文・型エラーなし）。
  - 実ブラウザでの非セキュアコンテキスト再現確認は、このセッションからは`claude-in-chrome`拡張未接続・`docker`コマンド不可のため実施できなかった。
- まーくんによるブラウザ確認（`http://homepi:5175/timer`）：完了。ストップウォッチ・ポモドーロ・手動記録モードそれぞれで開始〜記録までの一連の操作がエラーなく完了し、start/stop/resume/recordすべて200 OKであることを確認済み。
