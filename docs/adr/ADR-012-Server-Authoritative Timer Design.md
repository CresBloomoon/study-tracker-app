# ADR-012: サーバ主導のタイマー設計（Server-Authoritative Timer Design）

## ステータス
Accepted（採用）

---

## 背景（Context）

CPA-Dashboard において、タイマーは学習記録の根幹となる機能である。

従来のクライアント主導（LocalStorage 等）によるタイマー管理では、以下の問題が発生する。

- 端末間（PC / iPhone / iPad）で状態が一致しない
- ブラウザクラッシュやスリープ復帰で状態が壊れる
- タブ移動・リロード時に経過時間がズレる
- タイマー停止後に学習ログが記録されない事故が起こりうる

学習ログは「努力の証跡」であり、黙って失われることは許容できない。

そのため、タイマーは **サーバを唯一の真実（Single Source of Truth）** として設計する必要がある。

---

## 決定（Decision）

### 1. タイマーの真実はサーバが持つ

- タイマーの状態（RUNNING / STOPPED）は DB で管理する
- クライアントは状態を保持しない
- クライアントは「操作要求」と「表示」のみを担当する
- `/timer/current` API では `serverNow` を返却し、時刻の基準をサーバに統一する

---

### 2. タイマー開始処理の冪等化

- `POST /timer/start` は `clientRequestId` を受け取る
- 同一 `clientRequestId` による複数リクエストは、同一セッションを返す
- ダブルタップや通信再送による二重開始を防止する

---

### 3. タイマー停止と学習ログ作成の原子性保証

- タイマー停止処理と StudyLog 作成は、必ず同一トランザクションで実行する
- 処理途中でのクラッシュ時に、
  - 「タイマーは止まったが学習ログが存在しない」
  という不整合を防止する
- 学習ログが作成されない限り、停止は成立しない

---

### 4. 異常RUNNING（つけっぱなし）の自動修復

- RUNNING 状態が **18時間** を超えた場合、異常とみなす
- 異常を検知した場合、サーバは自動的に以下を実行する
  - タイマーを STOP
  - StudyLog を作成
- 上記処理はトランザクションで実行する
- `/timer/current` のレスポンスには以下を含める
  - `autoStopped: true`
  - `reason: EXCEEDED_MAX_DURATION`

---

## 結果（Consequences）

- 学習ログが黙って失われることがなくなる
- タイマー状態が端末・タブをまたいでも一貫する
- ブラウザクラッシュや長時間放置から自動復旧できる
- クライアント側の実装が単純になる
- タイマー機能全体の信頼性が大幅に向上する

---

## 検討した代替案（Alternatives Considered）

### クライアント主導（LocalStorage）によるタイマー管理
- 実装は容易だが、状態不整合・データ消失リスクが高いため却下
