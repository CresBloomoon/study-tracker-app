# ADR-013: Timer State and Time Counting Policy

## 背景（なぜ必要か）
タイマー機能は本プロジェクトの根幹であり、UI/バックエンド/DBがズレると利用者（自分）が混乱する。
特に「Stopで記録されるのか？」「ポモドーロの超過はどう扱うのか？」が曖昧だと、実装が破壊的に分岐しやすい。

本ADRでは、タイマーの状態(State)とポモドーロの進行(Phase)、および時間の集計方針を確定する。

## 決定内容（何を決めたか）

### 1. StudyLog生成ルール（最重要）
- StudyLogは **「記録(Record)」操作でのみ生成**する。
- **StopではStudyLogを生成しない。**
- 記録後は必ず **UI/サーバ状態ともに IDLE（初期状態）に戻す。**
- このルールは全モード共通（ポモドーロ / ストップウォッチ / 手動入力）。

### 2. ポモドーロ途中記録の扱い
- 例：10セット中、3セット目の途中で「記録」を押した場合
  - それまでに発生した実績分でStudyLogを生成
  - 以降のセット計画は破棄
  - 記録後は **1セット目のIDLE状態に戻す**

### 3. 時間カウント方針（最終決定）
- 集中時間（FOCUS）
  - 計画時間を超過した分もカウントする
  - UIでは超過分を色などで可視化する（例：緑）
- 休憩時間（BREAK）
  - あらかじめ設定した時間分のみカウントする
  - 超過して放置されてもStudyLogには含めない

理由：
- 達成感・モチベーションを最優先するため（「思ったより集中できたのに記録されない」を避ける）
- BREAKの放置超過は「努力量」ではなく「放置」である可能性が高く、記録の信頼性を下げるため

### 4. State / Phase の整理
- State（タイマー全体の状態）
  - IDLE / RUNNING / STOPPED
  - 「セッションが存在するか」「動作中か」の責務を持つ
- Phase（ポモドーロ内部の進行段階）
  - FOCUS / BREAK / DONE（または “awaiting next action” を表現）
  - セット内の進行を表す

StateとPhaseは別物として扱い、APIレスポンスでも混ぜない。

### 5. 後方互換（破壊的変更を避ける）
- 既存APIのレスポンス構造の変更は原則しない。
- 仕様の追加は「フィールド追加」「新エンドポイント追加」で対応する。
- Stopの意味を「記録」と混同しない（Stopは停止/一時停止）。

## 代替案（なぜ他案を捨てたか）

### 代替案A：Stop時にStudyLogを自動生成する
却下：
- Stopは「一時停止」の意味を持ちうるため、意図せず記録されるリスクが高い
- 「記録」は明示的アクションとして重要視しており、UX方針と矛盾する

### 代替案B：ポモドーロのBREAK超過も記録する
却下：
- 放置時間が混入しやすく、学習記録としての信頼性が落ちる
- “頑張った分を正しく褒める” という目的に反する

### 代替案C：StateとPhaseを1つの状態機械に統合する
却下：
- 責務が混ざり、UI/バックエンドの実装が複雑化する
- 仕様変更時の影響範囲が広がり、破壊的変更を誘発しやすい
